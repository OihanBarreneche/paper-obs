# Strategies and runs

All search methods should submit candidates to the same geometry judge. “Best” means the best **valid** candidate under the same problem, objective and engine version. Compare a complete score curve, number of judgements and elapsed time; an agent run also records model/tool calls, tokens and estimated money where prices are configured.

## Implemented methods

`search/baselines.py` provides `lattice` and `basin_hopping`. `lattice` is the floor: a grid (and, for discs, a staggered lattice) whose common scale it then grows. `basin_hopping` starts from the better lattice, shakes every shape of the best arrangement so far and lets the agents' own `polish` settle it, keeping what the engine ranks higher: the same tools an agent has, applied without reasoning, which is the reference an agent's choices must beat. A hop is billed one judgement per polish step plus one, and a run stops after five hops that find nothing. Pure random draws and a local walk of the lattice were removed: random anchors were almost never valid at a scale worth reading, and the walk always ended on the lattice it started from. They record convergence against a judgement budget. Randomness is carried by a seeded NumPy generator so that a problem, method and seed reproduce a run. Search operators initialize, mutate, relax, repair and locally fill candidates; they may generate invalid candidates, which the engine reports explicitly.

The **Search** tab runs these classical baselines and shows their curve beside the current candidate. The curve follows the measurement the objective promotes (`best_measure`, such as a container's side), while the primary score (`best_primary`, one over the side for a smallest container) still ranks the incumbents. Its **How do they work?** link opens a guide with one tab per baseline, its steps drawn as small schemas, with its cost in judgements and its limit. A non-exhaustive list names possible future method families without committing to them or offering inactive controls. The **Agents** tab is reserved for LangGraph workflows and their model/tool traces.

The optional agent stack has four LangGraph workflows, listed under [Workflow video sequence](#workflow-video-sequence). The first, `workflows/basic_agent_loop/`, displayed as **W1 · Basic agent loop**, is the base the others build on. It is a turn loop: `graph.py` opens every turn with a message saying where the run stands, builds a fresh agent with `create_agent` — which supplies the model → tools → model loop — and routes the run to another turn or to its end. `state.py` carries only the run record between turns; the arrangement under work lives in the tools, and the conversation does not survive a turn at all. The opening is a template, `prompts/turn.md`, filled by the shared `workflows/briefing.py`; the shared `workflows/session.py` opens each turn on the run's best arrangement, turns a finished turn into one run step, and adds up what the turn cost, without burdening the video-facing graph. `agent_tools/engine.py` connects tools to the deterministic judge.

**Memory.** Because a turn opens a new conversation, the agent's context is bounded by one turn instead of by a truncation rule, and three things cross from one turn to the next. The *state* is the run's best arrangement, on which every turn starts, described in the opening exactly as `read_state` would. The *journal* is one line per finished turn — the score it reached, whether it improved the run, the tools it used — written from the trace, so it costs no model call and cannot be forgotten. The *note* is the agent's own lesson: when a turn's reply or tool allowance runs out, `TurnNote` sends the last reply without tools and with the request in `prompts/note.md`, and that text answer ends the turn; a turn the agent ends early by answering without a tool call leaves its answer as the note the same way. The note replaces the previous one, so the agent rewrites what still holds rather than piling lines up, and it costs one of the turn's replies rather than an extra summarising call. A run ends when the agent calls `give_up`, when four turns in a row improve nothing, or on a ceiling. The tool ceiling refuses calls past it and lets the loop go on, so the next reply is the note rather than an abrupt end.

The opening also states what a model cannot guess from a coordinate list: the shape's exact size at scale 1, its width and height at rotation 0, whether a vertex or an edge is on top, and its symmetry period, all read from the domain's shape (`briefing.shape_facts`). The system prompt, `prompts/placer.md`, gives the agent the idea of an arrangement and leaves the continuous part to `polish`, `repair` and `fit_scale`. The model dialog's **temperature** (0 when left empty) is sent with every run. An endpoint that refuses one, such as OpenAI's reasoning models, is handed its own default and the field is greyed out; above zero, two turns that open on the same state can answer differently. The message that opens a turn restates every ceiling that applies to it — turns, replies, tool calls, time, money, output tokens — because they are the run's and not the model's, and the prompt asks for the work to happen in short replies and tool calls rather than in one long answer that the endpoint cuts. There is no image tool: rendered observations were tried and removed, as they cost a tool call and a thousand input tokens each without making runs reliably better. A run JSON file under ignored `runs/` records configuration, candidate snapshots, tool results, model replies, each turn's note, budget and outcome. Only replies a provider produced are counted as model calls: a message a limit writes to end a turn is not one. The browser shows each turn, the tool calls it made and every accepted improvement.

The run limits expose the number of **turns** (no ceiling by default) and two per-turn allowances: the **model replies one turn may make** (9 by default: eight to work and the note) and the **tool calls one turn may make** (12 by default). The form also starts with a **cost ceiling** of $0.15, applied once both token prices are entered, and an **output-token ceiling** of 4096, enough for a reply without reasoning; raise it well above 16k before turning reasoning on, since thinking is billed as output. A dash means the same thing in every field, the three counts included: no ceiling of that kind, which is also the shipped default for the clock. The form sends no run-wide call totals: the per-turn allowances, time and cost bound a run, since a total would have to guess how many agents a turn starts. A run with every field dashed is stopped only by the agent's own decision — or by whoever is watching it and presses Stop. A turn never spends more than the run has left, and an allowance of zero installs no middleware at all rather than a limit of zero. The **output-token ceiling** belongs to the run rather than to the model dialog, and a dash sends no field at all so the provider decides. A finished, stopped or failed run can be **resumed** (`runner.resume`, the `resume` field of `POST /api/agent-runs`): it goes on in its own document from its best arrangement, its journal and its notes, each workflow's `build` taking that arrangement as `start`. The limits entered for the resumption are added to what the run had already spent, and the document lists each resumption under `resumed`. A run cannot be continued from inside a turn: what is resumed is the state between turns. The server gives each run a process of its own (`create_app(processes=True)`, `multiprocessing` with the spawn method): model calls wait on the network, but the tools compute in Python, and runs sharing one interpreter would share one core. For the same reason, agents working at once within a run, such as parallel explorers, are threads of one interpreter: the run process therefore computes every tool's operator in a pool of worker processes (`agent_tools.engine.worker_processes`, started on demand up to the machine's cores), so each agent computes on a core of its own. Tests and `processes=False` compute in place. The parent writes the document as running first (`runner.open_run`, `runner.reopen`), so a client reading it at once follows it; the child runs `runner.carry_on`, the key reaches it as an argument in memory, and Stop sets an event both processes share. A run still ends with the server that started it, and the next `paper-obs serve` marks it failed. Every start, resumption or rerun first shows what it may spend — workflow, model, prices and every limit — and warns in red when neither a cost nor a turn ceiling is set; while a start is on its way no other can be sent. The run view reads a watched run again only once the last read has answered, and the listing reads again only the documents whose file changed, so a busy server is not buried under queued polls. Opening a problem shows its launcher even while one of its runs goes on, and **New run** stays available while the open run is watched, so several runs of one workflow can go on at once; the picker's running list follows each of them. The run picker lists the runs of this problem, of this workflow on any problem, or all of them, each with its best score and gap to the record. Below the open run, any runs of the same problem can be compared with it, or all of them at once: each one's best so far turn by turn, and what each spent, read from the listing's `track` (every new best as turn, score and gap) rather than from the run documents. A saved run can be deleted from the run picker; the API refuses to delete one that is still being written. Deleting moves the document to `runs/deleted/` (`runner.delete`): the run leaves the pickers but stays in the listing, marked `deleted`, so what it spent still counts in the statistics, and the picker's trash restores it (`runner.restore`). Removing a file from that folder by hand drops it from the totals. A run may also be told the published record of its problem, which is off by default: it is quoted in the source's own unit and, where the engine measures the same quantity, the opening states the run's best in that unit and how many percent better or worse it is (`briefing.reference_section`). It is presented as information that should not change how the agent works: a gap of several percent says the arrangement differs from the record's, a fraction of a percent says only tuning is left. A run that improves nothing for a number of turns in a row (**turns without progress**, 4 by default, a dash to disable) ends there, whatever those turns produced — an unbounded turn loop still needs a net under it, and a record makes drifting easier to see, not less worth stopping. The spend also records `model_seconds`, the time during which at least one model call was waiting on the provider (parallel calls counted once), which the run header shows as a share of the total duration. Token and cost usage are known after a provider response unless that provider supplies an earlier report. The current non-streaming implementation therefore cannot guarantee a hard stop *inside* a long model response; a per-response ceiling, when the caller sets one, and the user stop control reduce this risk. Money figures depend on user-entered prices and reported usage, and are estimates rather than invoices. An optional cache price bills the input tokens a provider reports as read from its prompt cache (LangChain's `cache_read`, or DeepSeek's `prompt_cache_hit_tokens`); left empty, they are billed at the input price, which errs high. The spend records `tokens_cached` beside the other counts. Time-of-day rates, such as DeepSeek's peak hours at twice its off-peak price, are not modelled: enter the rate the runs are billed at. The toolbar's chart icon opens a **Statistics** page over the run listing, filtered by period, workflow, problem, model and status. It opens on the run closest to the record (and how many beat it), the estimated spend with its tokens and cache share, and the runs; then every run in a sortable list (gap, turns and the turn of the best, duration, tokens, cost, date) whose rows open the run, eight at first and then in pages of twenty; for the problems picked from chips that give each one's run count (at first, the latest run's), each workflow's best gap and the spread of its runs on a line that reaches the record, or passes it; each run's cost against its gap; rings of what the runs used — models, workflows, problem families — by runs or by spend; and the spending per day. The comparison below an open run zooms by dragging across its chart: a flat stroke picks turns and fits the values reached there, a rectangle picks values too. The gap (`record_gap` in the listing, `briefing.record_gap`) is measured on the run's best valid arrangement in the record's unit, positive when it beats the record. The filtered runs export as CSV. A provider key entered in the model dialog is kept in this browser beside the provider and the prices, so a stopped and restarted lab does not need it retyped; the dialog can still forget it. It is never written into a run document, which is the file a run leaves behind and could be shared.

### Agent tools by objective

`agent_tools/engine.py` turns the operators of `search/` into LangChain tools, and `basic_agent_tools` offers a problem only the tools its objective can use, as `offered(kind)` lists them. The split is deliberate: the agent chooses the *idea* of an arrangement — which shape goes where, turned which way, which copy is the big one — and deterministic operators do the continuous work, which a model does badly by hand. Every tool answers the engine's verdict; none judges anything itself.

| What the agent may want to do | Tool | Offered for |
| --- | --- | --- |
| Read the arrangement, its verdict, every overlap with its separating direction and every overflow with the translation back inside | `read_state` | every objective |
| Find the room left (for a covering, the part of the target left uncovered) | `read_voids` | scale, count, total perimeter, covering |
| Read one shape's wall margin, overlaps and nearest gaps | `inspect_neighborhood` | packings |
| Place a whole arrangement; move, turn, resize, add or drop shapes | `place_shapes`, `edit_shapes` | every objective |
| Start from a construction: `grid`, `hexagonal` (discs), `varied` (free sizes), `cover` (covering) | `seed` | every objective |
| Move or turn a named group | `move_cluster` | every objective |
| Push overlapping shapes apart and overflowing ones back inside | `repair` | packings |
| Shake a few shapes, optionally turning them, and keep only improvements | `relax_local` | every objective |
| Tune the current idea to its last digits | `polish` | every objective |
| Set the best common scale for the current positions | `fit_scale` | scale, covering |
| Grow one shape's size, or all of them together | `grow_sizes` | total perimeter |
| Add a shape in a void, or drop conflicting ones | `fill_void`, `remove_overlapping` | count |
| Return to the best valid arrangement of the run | `restore_best` | every objective |

`polish` (`search/operators/polish.py`) is a seeded hill climb whose step follows the objective: it squeezes a minimized container towards its centre and repairs it, stretches a free common scale and repairs into it, trades size between two copies of a total-perimeter packing before regrowing every copy, shifts and turns the copies of a covering before refitting its smallest covering scale, gathers a derived covering, and tries one more shape in a void for a count. The first step settles a broken input, so an overlapping sketch is worth polishing. On the demo problems a call of 40 steps takes one to eight seconds. `repair` accepts a pass when it lowers the total violation severity, not when it raises the score: separating two shapes can enlarge a measured container, and a repair that refused that price never made such a candidate valid. The engine reports the translation that brings an overflowing shape back to the wall (`Containment.inward`), so the same pass also handles walls. Turns follow the problem's rotation policy and the outline's symmetry period (`PackableShape.symmetry_period`), so a pentagon is never turned by a multiple of 72° for nothing. The common scale is refused where the objective fixes it, and a shape's own `size` is accepted only where the objective sizes shapes one by one.

A workflow that declares a `sandbox` parameter also offers `run_python` on every objective ([The Python sandbox](#the-python-sandbox)).

The Agents tab shows the same tools without opening the code: *See the agent's tools* opens a viewer that lists each tool with its description, its arguments and the objectives it is offered on, starting from the objective of the problem at hand. Nothing in it is written for the interface. `GET /api/workflows/{id}/tools` builds the catalogue with `agent_tools/catalog.py`, which converts every tool exactly as a chat model receives it — its docstring, split into paragraphs, and its JSON Schema — and asks the workflow's menu which objectives offer it. Only the French is added, sentence by sentence in the interface's map, and a test fails when a docstring or an argument description changes without its French.

The timeline and the record follow the measurement the objective promotes, which is the same one the verdict panel headlines, so a total-perimeter run is read in the sum of its copies' sizes rather than in the perimeter proportional to it.

## Workflow video sequence

Plan **four** profiles, implementing each next profile only after measuring the one before it on the same problems and budgets:

1. **Basic agent loop** (implemented): one agent, engine tools, an explicit turn boundary and shared run limits. This is the cost/quality baseline.
2. **Strategist and executor** (implemented, `workflows/strategist_executor/`): each turn, a strategist without tools reads the best arrangement, the journal and the executor's last report, reflects on the last attempt and answers a structured `Plan` (LangChain `ToolStrategy`): one idea described by contacts and orientations rather than guessed coordinates, a few steps, and where the executor starts — the run's best, or the arrangement the last turn reached when its idea was still gaining, so an unfinished idea is not rebuilt from scratch. An idea counts as refuted only once polished to a plateau below the best. A fresh executor builds it with the same engine tools as the basic loop and reports back; the report is its note, and the plan is kept with the turn. It answers the tunnel vision the basic loop showed, where one agent kept polishing its first idea. Measure whether the strategist's extra call per turn buys more distinct ideas and better bests than the basic loop on the same budget.
3. **Parallel exploration** (implemented, `workflows/parallel_exploration/`): each turn, a strategist proposes one distinct idea per explorer (a structured `Ideas` answer), LangGraph's `Send` starts the explorers in parallel, each a fresh agent with the engine tools on its own `Workbench`: a copy of the best arrangement, or an empty board when the strategist sets the idea's `start` to `empty` for a new topology (explorers holding the best tended to fall back to it), and a `select` node lets the engine keep the best valid arrangement any of them reached (`AgentSession.merge`). Explorers cannot `give_up`; each one's tool calls carry its name as `branch_id`, and the turn's note is every explorer's report. The per-turn allowances apply to each explorer, so a turn spends up to `explorers` times as much; the shared run guard counts and stops them all. Each turn also records every explorer's own part under `lanes` (`AgentSession.lane`): its best arrangement with the engine's verdict, whether it beat that explorer's own best of earlier turns, its report and its idea; model replies, like tool events, carry the explorer's name as `branch_id`. The run view then offers one tab per lane beside the whole run, each with its own turn list, slider, record and trace, all read from the document. This tests diversity against an equal-cost solo baseline; a model never decides geometric validity.
4. **Research lab** (implemented, `workflows/research_lab/`): each turn, a planner proposes one distinct idea per team (the same structured `Ideas` answer as W3) and `Send` starts the teams in parallel. A team is a compiled LangGraph subgraph of three steps. Its *builder* builds the idea on its own `Workbench` with the engine tools and, when the `sandbox` setting is on, with `run_python` (below). Its *critic* is a second agent that may only read the builder's best arrangement (`read_state`, `read_voids`, `inspect_neighborhood`, a few calls) and answers a structured `Critique`: the weakest point, the engine's numbers that show it, and one move. The builder then answers the critique in its own resumed conversation, from its best arrangement, with a short allowance of its own. The critique *paid off* when the engine finds the team's best after the answer better than before it; nothing else decides it. The engine keeps the best valid arrangement any team reached, and the planner reads each team's report, critique and outcome on the next turn. Each lane is a team: it records `agents` (`builder n`, `critic n`, whose replies and tool calls carry those names as `branch_id`), the `critique` and a `revision` (`before`, `after`, `paid`, the builder's `answer`); the trace shows the critique as a card beside the plan. A turn spends up to `teams` times a builder's allowance, plus each critic's and each answer's. Each critique is kept as its own point of view per team; a peer critique, where one team's critic reads another team's arrangement, is a possible follow-up. Treat it as a demonstration of graph flexibility and inspectable orchestration, with an explicit spending cap and no presumption that it beats simpler methods.

### The Python sandbox

`agent_tools/sandbox.py` gives an agent `run_python`: a program that computes positions instead of guessing them. It runs in LangChain's Pyodide sandbox runner (`jsr:@langchain/pyodide-sandbox`), Python compiled to WebAssembly and run by Deno. Deno is only allowed to read and write the runner's own `node_modules` and to fetch packages from the Pyodide CDN and PyPI, so a program cannot read the lab's files, keys or runs, nor reach any other host. The Python wrapper `langchain-sandbox` is archived and requires `langchain-core<0.4`, so the tool calls the same runner directly. The program starts with `PROBLEM` (the engine's facts about the problem) and `CURRENT` (the arrangement under work, or `None`); if it ends on an arrangement, `{'placements': [...], 'scale': ...}`, the arrangement goes through `place_shapes` and the engine judges it like any other proposal. Any other value comes back with what the program printed, and an error comes back with the program's own traceback lines. Each call starts a fresh interpreter: about 5–8 s, and about 15 s the first time while Pyodide is fetched.

Deno is looked up on the `PATH`, then in `.sandbox/deno/bin/deno`. `.sandbox/` (ignored by Git) also holds Deno's cache and Pyodide; `PAPER_OBS_SANDBOX` moves it. To install Deno locally on Linux or WSL, unzip the `deno-x86_64-unknown-linux-gnu.zip` asset of a [Deno release](https://github.com/denoland/deno/releases) into `.sandbox/deno/bin/`. Without Deno, W4 refuses to start with the sandbox on; turning the `sandbox` setting off runs it without `run_python`.

The bundled **Demo Workflow** list contains four pentagons-in-square instances (2, 5, 8, 12), two circles-in-circle maximum-total-radii instances (2, 5) and two squares-covering-circle instances (2, 7). Each pair starts with a proved simple case and ends with a published construction without proof of optimality; the pentagons progress from a trivial case to recent harder constructions. These are *reference constructions*, not promised beatable records. The catalog snapshot records its check date and links each problem to its specific source page. See [pentagons](https://erich-friedman.github.io/packing/peninsqu/), [total radii](https://erich-friedman.github.io/packing/cirRcir/) and [covering](https://erich-friedman.github.io/packing/sqcovcir/).

The comparison panel filters saved runs by `problem_id` and then requires identical saved problem JSON; workflows may differ. It plots **valid adopted improvements** and shows calls, time and estimated cost. Budget differences receive a warning. Runs written while the loop was one long conversation recorded a step per tool batch, so compare scores against calls, time and money as well as against the displayed step index. References from the source pages should not be treated as verified optima unless their status is proved.

## Next integration contract

Before building separate genetic or reinforcement-learning pages, define one method-independent local solver contract: problem JSON in; candidate proposals and timestamped progress events out; the engine judges each proposal; a run stores its parameters, seed, budget usage, best valid candidate and full convergence curve. The method should not invent its own notion of geometric validity. The UI can then offer a **method selector** in one search workspace and compare methods side by side without multiplying navigation tabs.

Suggested order:

1. Measure the current agent tools against the existing baselines on identical problems and budgets. Inspect failed candidates and the final geometry, not score alone.
2. Adapt the existing baselines to a shared run/event schema and add one small external local heuristic adapter. Do not execute arbitrary uploaded Python on a shared server.
3. Add a **construct-and-repair** solver that proposes boundary, neighbor-contact and void placements. Existing grids are useful seeds but cannot express all contact patterns. It should handle each objective's feasibility rules explicitly and pay for every judge call.
4. Extend `basin_hopping` with controlled cluster perturbations or annealed acceptance, and record the convergence of each seed separately.
5. Test **large-neighborhood destroy-and-repair** on crowded cases: remove a subset of shapes and rebuild the freed region. Evaluate whether the improvement pays for its extra judgements before making it a general default.
6. Explore **verified bounds or exact optimization** only on suitably small/simple families, where a lower or upper bound can answer a different question from a good candidate: whether it could be optimal. Keep a numerical incumbent distinct from a proof.
7. Treat population-based evolution as an experiment after these baselines, with geometrically meaningful mutation and local repair; crossover alone is likely to produce invalid overlaps. Keep reinforcement learning as a later research option requiring a stable observation/action space, reward, training budget and benchmark set. Neither family deserves a dedicated tab yet.

The current catalog is broader than the current search methods. In particular, maximum-total-perimeter and covering instances deserve simple task-specific baselines before another complicated LLM graph is judged against them.

These priorities are hypotheses for this lab, not performance claims across all geometry families. Relevant primary work includes [contact-based construction followed by adaptive large-neighborhood search for circle bin packing](https://arxiv.org/abs/2001.07709), [basin hopping for unequal circles](https://arxiv.org/abs/1701.00541), and [continuous geometric optimization for large equal-circle instances](https://arxiv.org/abs/2303.02650). [Mixed-integer formulations for irregular nesting](https://arxiv.org/abs/2206.00032) and [global nonlinear models for several packing families](https://arxiv.org/abs/2605.04850) show both the promise and scaling limits of mathematical optimization. Evidence on learned policies is mixed: one [industrial comparison](https://arxiv.org/abs/2110.14535) favored a greedy heuristic, while a [2026 geometry-aware RL study](https://arxiv.org/abs/2606.10611) slightly exceeded its heuristic comparator on small polygon instances but retained a scaling gap on larger ones. Benchmark on this lab's own objectives before promoting any method.
